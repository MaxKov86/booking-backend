# Booking Backend

REST API для системи бронювання зустрічей (Calendly-lite). Express + TypeScript + MongoDB.

Працює у парі з окремим репозиторієм фронтенду (`booking-frontend`).

## Можливості

- **Генерація доступних слотів** з робочого графіка — з урахуванням тривалості слоту, буферу між зустрічами, мінімального часу на бронювання наперед і вже зайнятих часів
- **Бронювання з двошаровим захистом від конфліктів** — валідація на рівні застосунку + unique-індекс у БД проти race condition
- **JWT-автентифікація** — access + refresh токени, окремі секрети
- **Захист від IDOR** — авторизований користувач не може дістатись чужих даних, підставивши інший ID в URL
- **Email-нотифікації** — підтвердження клієнту й сповіщення спеціалісту (опційно, не блокують бронювання)
- **Керування розкладом** — робочі дні/години, тривалість слоту, буфер

## Стек

- **Express 5** — сам ловить помилки з async-хендлерів, без обгорток типу `express-async-handler`
- **TypeScript** (strict), **Mongoose**, **zod** для валідації вхідних даних
- **jsonwebtoken** + **bcryptjs** — автентифікація
- **nodemailer** — email

## Запуск

```bash
npm install
cp .env.example .env
```

Заповни `.env` — інструкції з отримання MongoDB Atlas connection string і генерації `JWT_SECRET` прямо у файлі.

```bash
npm run dev      # http://localhost:4000
npm run build    # компіляція в dist/
npm start        # продакшн
npm run lint
```

## API

| Метод | Шлях | Захист | Опис |
|---|---|---|---|
| `POST` | `/api/auth/register` | — | Реєстрація спеціаліста |
| `POST` | `/api/auth/login` | — | Логін, повертає пару токенів |
| `POST` | `/api/auth/refresh` | — | Новий access за refresh-токеном |
| `GET` | `/api/auth/me` | 🔒 | Поточний користувач |
| `GET` | `/api/availability/:userId` | — | Конфігурація розкладу |
| `PUT` | `/api/availability/:userId` | 🔒 owner | Оновити розклад |
| `GET` | `/api/availability/:userId/slots?date=` | — | Вільні слоти на дату |
| `POST` | `/api/bookings` | — | Створити бронювання |
| `GET` | `/api/bookings/:userId` | 🔒 owner | Список бронювань |
| `PATCH` | `/api/bookings/:bookingId/cancel` | 🔒 owner | Скасувати |

## Ключові технічні рішення

### Двошаровий захист від подвійного бронювання

**Шар 1 — валідація "час є серед доступних слотів".** Роут не просто перевіряє "чи вільно", а генерує слоти тим самим `slotGenerator`, що віддає їх клієнту, і шукає точний збіг. Без цього можна було б надіслати довільний `startsAt` (03:17 ночі, посеред перерви) і забронювати час поза сіткою.

**Шар 2 — unique partial-індекс у БД.** Між генерацією слотів і записом інший клієнт може встигнути зайняти той самий час — перший шар цього не ловить. Індекс на рівні MongoDB гарантує відмову другого запису незалежно від таймінгу; помилка `11000` перетворюється на `409`.

Це класична TOCTOU-проблема: перевірка й дія не атомарні, тому перевірки самої по собі недостатньо.

### Access + refresh токени

Не один довгоживучий токен: access (15хв) надсилається з кожним запитом, тому ризик перехоплення вищий — живе коротко. Refresh (7 днів) використовується рідко. Різні секрети — компрометація одного не дає підробити інший.

### Захист від IDOR

`requireAuth` перевіряє, що юзер залогинений. `requireOwnership` — що він працює **зі своїми** даними. Без другого будь-який авторизований користувач читав би чужі бронювання з персональними даними клієнтів, просто змінивши `:userId` в URL.

### Захист від user enumeration

Логін повертає однакову помилку і для "юзера не існує", і для "пароль невірний" — інакше перебором можна з'ясувати, які email зареєстровані.

### Час у UTC

`startsAt`/`endsAt` зберігаються як `Date` (MongoDB тримає в UTC), а не як окремі рядки дати й часу. Конвертація під локальну зону користувача — на фронтенді при відображенні.

**Задокументоване спрощення:** робочі години трактуються як UTC напряму, без урахування часової зони спеціаліста. Повноцінна підтримка таймзон — наступний крок розвитку.

## Деплой на Render

`render.yaml` у корені — Render підхоплює його автоматично (Blueprint).

1. **New → Blueprint**, вкажи репозиторій
2. У **Environment** додай секрети (у `render.yaml` вони `sync: false`, щоб не потрапляли в git): `MONGODB_URI`, `JWT_SECRET`, `CORS_ORIGIN` (URL фронтенду), опційно `SMTP_*`
3. **MongoDB Atlas → Network Access**: додай `0.0.0.0/0` — IP Render динамічний

### Підготовка до контейнерного хостингу

- **`app.listen(PORT, '0.0.0.0')`** — усередині контейнера `localhost` означає "лише цей контейнер"; платформа не достукалась би до сервісу, деплой "піднявся" б, але health-check провалився
- **`PORT` з env** — платформа задає його сама
- **`process.exit(1)` при недоступній БД у production** — краще невдалий старт, ніж "здоровий" сервіс, що віддає 500 на кожен запит. Локально навпаки: сервер піднімається, щоб було видно причину
- **`CORS_ORIGIN` приймає список через кому** — Vercel створює унікальний URL для кожного preview-деплою

**Особливість free-плану Render:** сервіс присинає після ~15хв без запитів, перший запит потім займає 30-60с (холодний старт).

```
src/
  models/       # User, Availability, Booking (Mongoose-схеми)
  routes/       # auth, availability, bookings
  services/     # slotGenerator, authService, emailService
  middleware/   # auth.middleware (requireAuth, requireOwnership)
  config/       # db.ts
  app.ts        # Express: CORS, JSON, роути, error-handler
  server.ts     # точка входу
```
